## 一、根因（已实证，非推测）

用 Python **逐字复刻 App 实际发出的完整 URL** 打真实 API：

```
https://api.open-meteo.com/v1/forecast?...&wind_speed_unit=ms
  &forecast_days=16&past_days=1&timezone=auto&timeformat=unixtime
```

真实响应：

```json
"daily": {
  "sunrise": [1789422908],     ← 整数（epoch 秒）
  "sunset":  [1789467833]      ← 整数
}
```

而 DTO 声明为 `[String?]?`（字符串数组），依据是 `ARCH-A1 §1.4` 的断言
「sunrise/sunset 绕过 `timeformat=unixtime`，仍为 ISO 本地墙钟字符串」。

**该断言是错的。** 后果：真机 JSON 解码 100% 抛 `typeMismatch`
→ 主屏恒显示「格式问题」→ 实况、逐小时、逐日**全量不可用**。

### 为什么 CI 一路全绿（这才是最贵的教训）

单测 Stub 里的 sunrise 写的正是 `"2026-09-11T05:53"` 这种 ISO 字符串——
**与实现的假设同源**。测试数据和被测代码共享同一套错误假设，
所以这个缺陷对 CI 完全不可见，只在真机上暴露。

已固化为铁律（`docs/CI-pitfalls.md` P-18）：

1. 任何对**第三方 API 行为**的断言必须用**真实响应**验证过——
   不能只信文档，不能只靠 Stub。
2. 验证手法固定为「Python 复刻真实 URL + 逐字段比对 DTO 类型」。
3. 修完必须反问「为什么现有测试没抓到」，若答案是「同源」，
   则必须补一个真机形态的用例。

## 三、三路并行审查结果

### ① 跨链路「真机契约」审查 — 无同类缺陷 ✅

对四条链路全部复刻真实 URL 并逐字段比对类型：

| 链路 | 域名 | 验证字段量 | 结论 |
|---|---|---|---|
| 主链路 forecast | `api.open-meteo.com` | 25 个叶子字段（hourly 全 408 元素、daily 全 17 元素扫描） | ✅ |
| 空气质量 | `air-quality-api.open-meteo.com` | 8 | ✅ |
| 历史天气 | `archive-api.open-meteo.com` | 5 | ✅ |
| 地理编码 | `geocoding-api.open-meteo.com` | 6 × 命中条数 | ✅ |

- `timeformat=unixtime` **仅主链声明**，其余三链未用 → 无第二个
  sunrise/sunset 式的参数副作用坑。
- 所有 `Int` 字段实测皆整数（`relative_humidity_2m`、`weather_code`、
  `is_day`、`us_aqi`、`european_aqi`、`utc_offset_seconds`）→ 不触发 Int 解码失败。
- 非可选元素数组（`hourly.time` / `temperature_2m` / `weather_code`、
  `daily.time` / `tmax` / `tmin`）全量扫描**零 null**。
- 所有空气/历史/地理 DTO 字段均为可选（`Double?` / `Int?` / `[T?]?`），
  整键缺失不炸。
- 地理编码**无命中时服务端不返回 `results` 键**（只返回 `generationtime_ms`），
  DTO 的 `results: [Place]?` 正确吸收 → 不会把「无结果」误判成失败。

### ② 修复本身的深度审查 — 正确 ✅，另发现 1 个既有缺陷 ⚠️

- **时区语义等价性（数值验证）**：同一真实日出，ISO 路径（按
  `utc_offset_seconds` 解释）与 epoch 路径产出的**绝对 Date 一致**，
  差异仅 ±59 秒——因为 ISO 字符串只有 `HH:mm` 没有秒。
  epoch 路径不依赖 `utc_offset_seconds`，**反而更稳**。
- **`FlexibleTime.init` 健壮性**：
  - JSON 整数可被 `decode(Double.self)` 成功解出（整个修复的命门成立）；
  - `null` 元素被 `Optional` 合成在 `init(from:)` **之前**拦截 → `nil`，不抛错；
  - 布尔值 `true` 会正确抛类型错（不会像 `decode(NSNumber.self)` 那样变成 `1.0`）；
  - 真实 epoch ~1.8×10⁹ ≪ 2⁵³，无精度损失。
- **缓存兼容**：`FlexibleTime` 只存在于**不落盘**的 DTO 中，
  `WeatherSnapshot` 端 `sunrise/sunset` 仍是 `Date? = nil` → 旧缓存缺键安全。
- **回归风险**：`decodedSunTime` 三重保护（数组可缺 / 下标越界 / 元素 null），
  今日行、昨日行、逐日行共用同一函数，语义一致。
- ⚠️ **既有缺陷（与本修复无关，修复前即存在）**：
  `ContentView.swift:448-453` 与 `DailyForecastRow.swift:170-174` 的
  `timeFormatter` **未设置 `timeZone`**，用**设备时区**渲染。
  用户查**外地城市**时，显示的既不是当地时间、也没有标注——
  是个真实的 UX 错误。修法：格式器 `timeZone` 设为 `City.timeZoneIdentifier`。

### ③ 错误处理与可诊断性审查 — 这次「只能截图问人」的根因 ⚠️

**「格式问题」这句话的来龙去脉**：

```
WeatherService.swift:51   throw WeatherError.decoding(error.localizedDescription)
WeatherViewModel.swift:383-384  case .decoding(let detail): "数据解析失败：\(detail)"
```

`localizedDescription` 在中文设备上就是「由于数据格式有问题，无法读取该数据」。
**它丢掉了 `codingPath`（到底是哪个字段解不出来）和 `debugDescription`**
——这两个恰好是能一眼定位问题的信息。

| 问题 | 位置 | 后果 |
|---|---|---|
| 解码错误信息被压缩成一句话 | `WeatherService.swift:51` | 丢失 `codingPath`，无法定位字段 |
| 全库无 `os.Logger`/`os_log`，只有 `print` | 全仓 | 解码失败**无日志**，真机无从诊断 |
| `network` 把超时/DNS/非HTTP 压成同一 case | `WeatherProviding.swift:11-20` | 故障域不可细分 |
| `network` 的 detail 是**英文技术文本**直接给用户看 | `WeatherViewModel.swift` | 用户看不懂 |
| App Group 权限失败**静默** | `WeatherViewModel.swift:173-175` | 只 `print`，用户完全无感知 |
| 无错误上报 / 诊断页 / 可复制详情 | 全仓 | 「只能截图问人」 |

**已设计的最小改动方案（待批准后实施）**：

1. `WeatherService.swift:47-52` 解码 `catch` 改为
   `catch let de as DecodingError { logger.error("\(de.codingPath) \(de.debugDescription)"); ... }`，
   并加 `Logger(subsystem: "Core", category: "decode")`。
2. `WeatherViewModel.swift:372-386` 文案按故障域重写：
   - 网络类 → 「网络连接异常，请检查网络后下拉重试」
   - 服务端类 → 「天气服务暂时不可用（错误码 \(code)），请稍后再试」
   - 解析类 → 「天气数据暂时无法解析，已记录异常，建议反馈给开发者」
   - App Group 异常 → 「小组件共享异常，请检查 App Group 权限」
3. `#if DEBUG` 下在 `ContentView.swift:92-99` 的 `.failed` 分支
   把原始 detail 作为可展开区域暴露，便于真机排障。

## 四、过程中修掉的 CI 失败（run35）

run35 失败**不是产品代码问题，而是我写的测试代码编译错误**：

`[FlexibleTime?]?` 的元素访问是**双层可选**——`daily.sunrise?.first`
的类型是 `FlexibleTime??`，再链 `?.isoString` 只能解一层 →
`value of optional type 'FlexibleTime?' must be unwrapped`（6 处）。

**关键规律**（已记入 `CI-pitfalls.md` P-17）：
`?.first?.member` 是否合法**取决于数组元素本身是否可选**——

- `[DailyForecast]?` → `?.first` 得 `DailyForecast?`（单层）→ 能编过；
- `[FlexibleTime?]?` → `?.first` 得 `FlexibleTime??`（双层）→ 必断。

所以这个写法**有时能编过有时编不过**，不能凭印象判断。

修法：`DecodingTests` 新增 `sunTime(_:at:)` 助手做显式索引取值，
统一返回扁平的 `FlexibleTime?`；`MapperTests` 同型写法改显式解包。

**排查同时做了「不过度修改」的克制**：全仓扫描该模式命中 9 处，
但其中 8 处操作的是元素**非可选**的 `[DailyForecast]?` / `[Place]?`，
已被 run32/run34 绿色 CI 证明能编过——**不动**。

另排除一处误报：CI 日志里的「找不到可用 iPhone 模拟器」`::error::`
只是 GitHub Actions 回显脚本文本，实际选中了 `iPhone 15 Pro`，模拟器步骤正常。

### CI 过程中的两个坑（已写入 `docs/CI-pitfalls.md` 与技能）

1. **run 被 `cancelled` 不等于失败**：连推两个 commit 时，GitHub 并发策略
   会取消还在跑的旧 run。`0324b84` 那次就是这样被 `154b152`/`591fc8b` 顶掉的。
   → 盯 CI **必须按 SHA 过滤**，不能取 `runs[0]`。
2. **push 连续失败的真因是环境变量代理**：`HTTP_PROXY`/`HTTPS_PROXY`
   =`127.0.0.1:2586` 是坏出口（502）且优先级高于 git 默认。
   绕行：`git -c http.proxy=http://127.0.0.1:7897 -c https.proxy=... push`。
