## 0. 本机实测的关键结论（推翻了几条初始假设）

| 实测项 | 结果 |
|---|---|
| `open-meteo` `minutely_15=precipitation,precipitation_probability` | **可用**，北京返回 96 点/24h，含概率。→ "分钟级"不必等新源 |
| `api.rainviewer.com/public/weather-maps.json` | **免 Key 可用**，past 12 帧 + host + satellite 槽位 |
| RainViewer 瓦片 z3/z4/z5 北京 | **有真实回波**（我下载解码确认，华北华东雨带清晰）；z6+ 返回 `Zoom Level Not Supported`（1370 字节占位图） |
| RainViewer `nowcast` | 本次为空数组（0 帧）→ nowcast **不能承诺** |
| `air-quality` 六污染物（北京） | pm2.5/pm10/CO/NO2/SO2/O3 全部 48/48 有值 |
| air-quality 花粉（pollen_*） | **HTTP 400**，中国不支持 → 别做 |
| `forecast` 逐时 uv_index/visibility/snow_depth/cape/freezing_level_height/evapotranspiration | 全部 24/24 有值 |
| `weather.com.cn/data/alarm_xml/alarminfo.xml` | 免 Key 可抓，结构完整（105 站、16 类含 Typhoon、含 signalLevel/issueTime/relieveTime/issueContent），**但 dt=20240805144545，数据冻结在 2024-08-05** |
| 官方预警（Apple 中国大陆走**和风天气**，付费 Key）；NWS `api.weather.gov` 对中国 404；MET Norway properties 只有 meta/timeseries | 免 Key 源里**没有可信的中国官方预警** |

## 1. 标杆产品逐个拆解（各 2-3 条最值得抄）

### 彩云天气（国内标杆，2.9 万评分 3.8，App Store 页 + 7.4x 更新日志）
- **数据呈现**：把降水做成**一条独立的"降水条"而不是图表**——未来 120 分钟绿/黄/红三色条，标概率+强度。左滑即得，不用进二级页。更新日志反复出现"降水即将开始"横幅文案。
- **交互**：卡片级**开关**（7.56.0 "AQI 卡片支持关闭"、7.59.0 "40+ 项数据自由组合"）——用户自己决定首页放什么，这是"信息过载"的正解。
- **我们没有的源**：自家雷达 mosaic + 街道级定位 + 台风路径（都是自建/合作，非免 Key）。

### 墨迹天气（2.9M+ MAU，官网 mjsoft）
- **数据呈现**：**"大雨定点速报"= 暴雨前 8h 起、48h 内的逐小时决策建议**——不是数据，是"该做什么"。另有 48h 分钟级地图（降水/风力/空气质量三态切换）。
- **交互**：把"风"做成独立入口页（风详情 + 实况风场图 + 天级/小时级阵风），而非塞进逐时列表。
- **我们没有的源**：AI 引擎 + 40 项指标自有源。

### Apple Weather（用户默认基线）
- **数据呈现**：**信息层级最干净**——第一屏只有：当前大温度 → 一句摘要 → 逐时横滑条 → 10 天条 → 一张"降水/温度/空气质量"折线图卡；地图和全部细节收在**左下角折角地图图标**后面。摘要直接写成句子："Rain starting in 18 minutes"（iOS14 起）。
- **交互**：地图内**图层切换器**（右上）+ **底部时间轴 scrubber**（可拖动/播放，降水与风图层才有）。
- **降级做法（对我们最有参考价值）**："Next-Hour"仅美/英/日/澳/爱，其他地区**自动退回 12 小时地图**；部分国家只有底图无降水层。→ 官方就是"有就给，没有就降级，不撒谎"。
- **来源**：iphonefilez 实测文 + BGR 评测 + 百度百科（明确记载"中国大陆极端天气由和风天气提供、空气质量由和风提供"）。

### oscar-weather（开源同源，最值得抄的架构）
- **数据呈现**：README 明列 **土壤温度/湿度多深度（0–81cm）、ET₀ 蒸散、花粉分型、almanac 气候均值 vs 昨天对比**——全部走 Open-Meteo 免 Key。
- **交互**：**hourly detail 可切"章节时间轴"**（chapters 而非连续曲线），每章一个天气事件。
- **注意**：它的雷达是自建瓦片 + RainViewer 全球叠加，等于替我们验证了 RainViewer 路线可行。

### OSS Weather（Akylas，MIT，449 star）
- **数据呈现**：**逐分钟降水**与雷达图并列；**Compare Models（多模型对比）** 是它最独特的呈现——同一城市 GFS vs ECMWF vs Météo-France 并排，模型分歧即"不确定性"。
- **用户呼声（GitHub issues 实测）**：`#447` 请求逐时图常显阵风、`#363` 请求阵风指示器、`#385` 请求图表缩放状态记忆——**"逐时图上要同时有平均风+阵风"被独立提出两次**。我们已做阵风，方向对。
- 缺失：明确列 "No weather alerts"——开源界普遍没有预警。

```

  ├─ 雷达地图（地图页，非主页）★新增
  ├─ 生活指数（已有）

  └─ 数据链路健康面板（已有）
```

## 4. 预警/雷达缺失时的降级模式（具体设计）

**核心原则：区分"没有数据"和"有数据但旧了"，两者都不显示，但理由不同。**

### 4.1 预警的三态模型
```
.covered(nearby)   → 橙色横幅 + 本地通知
.covered(far)      → 折叠行"附近有预警"（不推送，避免误报疲劳）
.stale / 无源      → 折叠行，文案固定为"未接入官方预警源，突发天气请以气象部门发布为准"
```
**关键：`.stale` 态必须显式上屏，不能静默消失。** 依据：我们实测 alarm_xml 能返回结构完整的 105 站 16 类预警，但数据冻结在 2024-08-05——这正是"能解析但不可信"的陷阱。必须做**新鲜度断言**：解析 `dt` 字段，与当前时间差 > 6h 即判 `.stale`，不展示任何内容。这是我们多源账本已有的 EV-1/EV-3 摘除判据可以直接复用的机制。

**替代预警（现在就能做，A 类）**：用我们**已有**数据自造"风险提示"，但必须与官方预警视觉上区分命名——叫「我们的推算」，不叫「预警」。可算的：
- `minutely_15` 概率 ≥ 60% 且持续 3 个点 → "约 X 分钟后开始降水"
- `wind_gusts_10m` ≥ 50 km/h → "阵风偏强"
- `weather_code` 命中 95/96/99（雷暴）→ "可能有雷暴"
这三类覆盖了国内用户 80% 的实际需求，且**语义诚实**。

### 4.2 雷达的四态模型（我们能自洽，因为有 minutely_15 兜底）
```
.forecast(国内)    → 逐时降水概率（已有）
.forecast(欧美)    → minutely_15 2h 概率条
.radar(有回波)     → 地图 + 雷达图层
.radarUnavailable  → 地图页仍可进入，但只显示"本区域暂无实时回波，下方为模型降水概率"
```
- **zoom 降级**：RainViewer 实测 z3/z4/z5 有数据、z6+ 返回占位图。所以地图**最大 zoom 限制在 5**，并对 z>5 不发请求（省流量+避免占位图糊屏）。
- **nowcast 帧为空**（实测 0 帧）→ 时间轴只到"最新实况帧"，不显示任何未来帧。**绝不显示空白 scrubber**。
- 底图不能省：即使无回波，地图 + 城市位置 + 概率色斑仍有价值。Apple 在部分地区就是这么做的。

### 4.3 首页条永远存在
雷达/预警都可能没有，但 **A2 降水条只需要 minutely_15**（实测可用）。所以第一屏永远有一个"接下来会不会变"的答案。**这是我们对抗"数据不全"的最强底牌。**

## 6. 一句话结论

下一轮**只做 A 类，A1（雷达地图）+ A2（降水条）优先捆绑落地**——这两个用现有免 Key 源已实测可行，难度中低，且精准命中国内呼声 Top 1 与 Top 2。B 类（预警/台风）在拿到合规数据源前，一律走"三态 + 显式陈旧断言"的降级模式，**不要为了补齐而编造**。同时用 A7（卡片可关）治第一屏臃肿。
